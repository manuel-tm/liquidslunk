# Backend (`slunk-be/`)

> Keep this page up to date: any change to the backend's stack, structure, scripts or conventions updates it in the same change.

The backend implements the whole base design ([1_introduction.md](../design/1_introduction.md), phases 0 to 4), with credits as lines from phase 0 of [2_credits.md](../design/2_credits.md), and alternate names, credited names, alternate titles and the import's use of them from [3_alternate_names.md](../design/3_alternate_names.md), phases 0 to 3:
- the database connection, the migration runner with backup retention, and the migrations;
- a GraphQL server with a `health` query;
- the media context: registering files, browsing the library on disk, serving the files' bytes, and file links;
- the catalog context: artists and labels with their alternate names, releases with their formats, media and labels, tracks, disc titles, alternate titles, credits, and suggestions for importing a folder, matching artists by any of their names;
- the tagging context: tag definitions, their values on releases and tracks, the lists' tag filters, and bulk edits;
- the library check: what changed on disk since files were registered, and gaps in the catalog.

## Stack

| Piece | Choice |
|---|---|
| Runtime | Node 26, which runs the `.ts` files directly: there's no build step |
| HTTP + GraphQL | Express 5 and Apollo Server 5 (`@as-integrations/express5`), on `graphql` 16 |
| Database | SQLite through better-sqlite3, queried with Kysely |
| Types | kysely-codegen for the database, graphql-codegen for the resolvers |
| Batching | DataLoader, for the related rows a page shows |
| Audio | music-metadata, which reads durations and embedded tags |

Two versions are held back on purpose:
- `better-sqlite3` stays on 12, because kysely-codegen supports nothing newer.
- `graphql` stays on 16, which Apollo Server 5 requires.

## Configuration

Every npm script loads `slunk-be/.env` if it exists (`node --env-file-if-exists=.env`).

| Variable | Meaning |
|---|---|
| `SLUNK_DB` | Required. The database file. A relative path resolves from `slunk-be/`. Its folder must already exist. |
| `SLUNK_KEEP_BACKUPS` | How many backups `slunk-backups/` keeps, a whole number from 1. Default `10`. |
| `PORT` | The server's port. Default `4000`, which the frontend's Vite proxy expects. |

The server listens on `127.0.0.1` only, so nothing else on the network can reach it. It also refuses (403) any request whose `Host` isn't `localhost`, `127.0.0.1` or `[::1]`. Without that, a web page could point a domain it controls at 127.0.0.1 (DNS rebinding) and read the API, which can list any folder on the disk.

In development, `SLUNK_DB` points into `dev-library/`. Put sample music files and images there to register them. Never point it at a real music library.

## Contexts

The domain lives in contexts, like Phoenix's (design §6). Each one is a factory in `src/slunk/` that takes the repositories it needs and returns plain functions:

- **The context** declares the repository interfaces it needs, next to it: `src/slunk/media/repository.ts` declares `FilesRepository` and `FileLinksRepository`, `src/slunk/catalog/repository.ts` declares `CatalogStore`, every repository the catalog uses, and `src/slunk/tagging/repository.ts` declares `TaggingStore`.
- **`src/repo/`** implements them for SQLite. `createStore(db)` builds them all over one connection, as a `Store`: every context's store in one.
- **`src/server.ts`** wires them together once, at startup: `createMedia({ files, fileLinks, library })`, `createTagging({ store })`, `createCatalog({ store, media, tagging })`, then `createLibraryCheck({ media, catalog })`. A context can call another one: the catalog asks media to read and register files, and tagging to save a track's tags.
- **Resolvers** only call context functions. The one exception is `health`, which is about the backend itself and asks the repo directly.

Repositories turn rows into the context's own types: `snake_case` columns become `camelCase` fields (`size_bytes` → `sizeBytes`), and 0/1 flags become booleans. They also set `updated_at` on every update.

**Transactions.** `store.transaction(fn)` runs `fn` with repositories bound to one transaction, so a mutation that writes several tables writes all of them or none. Inside a transaction, nested calls join it. Reading files (hashing, durations) happens before the transaction starts, so the write lock is never held during disk I/O. `media.prepareFiles(paths)` reads files without writing anything, and `media.insertPrepared(tx, prepared)` registers them inside the transaction. That's how saving a release's tracks registers new files and creates their tracks in one go, and leaves no file registered if it fails.

When one context writes inside another's transaction, it takes the transaction's repositories rather than its own: `media.insertPrepared(tx, …)` and `tagging.setTagsWith(tx, …)` do. A context's own store isn't bound to the transaction, and SQLite has one connection, so starting a second transaction from it would wait forever.

**Text** is normalized to Unicode NFC and trimmed before it's saved (`text.ts`), so " Rock " is saved as "Rock". The same characters can come in two forms, "é" as one code point or as "e" and an accent, and NFC makes them one, so either finds the other. NFKC isn't used, since it would rewrite what's printed ("E=MC²" would become "E=MC2"). Searches are normalized the same way. Paths aren't text: they're kept as they are on disk. The database's CHECKs still reject anything left empty.

**Errors** meant for the user are plain `Error`s with a readable message ("There's no file at …", "The release still has 3 tracks. Delete them first."). The triggers' messages pass through as they are. `slunk_web/errors.ts` rewrites SQLite's constraint errors into words a form can show: `UNIQUE constraint failed: tracks.file_id` becomes "That file is already a track's audio". GraphQL returns the message as is.

## The media context

`src/slunk/media.ts` registers files and reads the library. It never writes to the user's files: `src/slunk/media/library.ts` only reads them.

- **Paths** are relative to the database's folder, and normalized (design §4.1). The folder itself is `""`, and paths above it start with `../`.
- **Browsing** (`folder`) lists a folder's subfolders and the files directly inside, following symlinks. Each subfolder says whether it, or a folder inside it, holds registered files. That's an index range on `files.path`, and it also works for folders above the database's folder.
- **Scanning** (`folderFiles`) lists every file in a folder and its subfolders. It doesn't follow symlinked folders, so a link loop can't make it run forever.
- **Left out of both:** hidden files and folders (names starting with `.`, like `.DS_Store`), and Slunk's own files: the database, its `-wal`/`-shm`/`-journal` files and `slunk-backups/`.
- **Types** come from the extension, in `file_types.ts`:
  - `music`: aac, aif, aiff, alac, ape, dff, dsf, flac, m4a, mp3, mpc, oga, ogg, opus, wav, wma, wv;
  - `image`: avif, bmp, gif, heic, jpeg, jpg, png, svg, tif, tiff, webp;
  - `other`: everything else.
- **Registering** reads each file's size, mtime (in whole seconds) and SHA-256 (lowercase hex), streaming the file through the hash. Paths already registered are returned as they are.
- **Updating** changes the type, or the path, to relink a file that moved. A new path is read again, and it can't be one another file is registered at.
- **Deleting** removes only the record, and fails while anything uses the file: a track's audio, a cover, a picture or a file link. The error says what uses it.
- **File links** connect images and other files to releases, artists and tracks, each with an optional note. Saving an owner's links replaces them all.
- **Audio** (`audio.ts`) reads a file's duration and embedded tags with music-metadata. A file it can't parse has no duration and no tags.
- **Relinking and rehashing** (`relinkFiles`, `rehashFiles`) fix what the library check finds. Relinking points a file at a new path, like editing its path. Rehashing reads a file's size, mtime and hash again; it reads every file first, so one that's gone fails before anything is saved.

### Serving files

`GET /raw/files/:id` (`files_controller.ts`) sends a registered file's bytes, read-only, for viewing and playback. Express sets the content type from the extension, and answers Range requests, so audio can seek. An unknown id, or a file missing on disk, gets a 404.

The path is under `/raw` so it can't collide with the frontend's `/files` pages ([design Appendix C](../design/1_introduction.md#appendix-c-file-bytes-are-served-under-raw)).

## The catalog context

`src/slunk/catalog.ts` holds what the user catalogs: artists, labels, releases, tracks, disc titles, credits, and the two lists the user manages (release formats, release media).

- **Lists** share one repository and one set of functions (`listItems`, `createListItem`, …), with a `kind`. Names are unique ignoring case.
- **Alternate names** ([3_alternate_names.md §4.2](../design/3_alternate_names.md#42-design-decisions)) are other names an artist or label goes by: other spellings ("ALIKA"), initials ("R. Fukui"), names in other scripts ("福居良"). An artist's can be real names.
  - They're saved with their artist or label, as an ordered list (`alternateNames`): a name with an id keeps its row, one without is added, and names left out are deleted. Left out entirely, they stay as they are.
  - Names are cleaned like other text, and a blank one is left out. They compare exactly, case included, so "ALIKA" isn't "Alika".
  - A save is refused, with a message, when a name is given twice, or when one is the main name, unless it's a real name.
  - A name the list gives without an id, which the artist already has, keeps its row, and so the links credited with it.
  - Names can trade places between rows in one save. The repository first moves renamed rows clear of the unique (owner, name) index, as tracks are renumbered.
  - The artist and label lists' search, and so their pickers, match the main name or any alternate name.
  - A label's are simply replaced. Left out, they stay as they are, except one the label is renamed to, which goes.
- **Credited names** ([3_alternate_names.md §6](../design/3_alternate_names.md#6-backend)): every artist link (a release artist, a track artist or feature, an artist on a credit line) can be credited with one of the artist's alternate names, the name printed there. Without one, it shows the main name.
  - A link is given as `{ artistId, creditedAs }`, the name as printed, and resolved by `creditedNames()`, once per transaction: blank, or the main name, is no credited name; one of the artist's alternate names, compared exactly, is that name; anything else is added to them. An added name gets a language only when its script gives it away: kana are `ja`, Hangul `ko`.
  - An artist given twice on a list, or on a credit line, is kept once, as first credited.
  - Who performs a track (below) keeps the release's credited names when it falls back to the release's artists.
  - `ArtistName.uses` counts the links credited with a name, and `Artist.mainNameUses` those that show the main name.
- **An artist's names and its links** are saved together (`saveArtistNames`), so every link keeps showing what it showed:
  - Removing a name that links are credited with credits them with the main name instead (`uncredit`), then deletes it.
  - Renaming an alternate name renames it on its links: that's how a misprint is fixed.
  - A rename shows on the links with no credited name. With `keepOldName`, they're credited with the old name instead, added to the alternate names if it isn't one (`creditMainNameLinks`). That happens first, so the links of a name that goes in the same save don't get it.
  - With the list left out, renaming the artist to one of its alternate names promotes it: its links lose their credited name, and the name goes, unless it's a real name, which stays as one.
  - A real name kept with the same text as the main name leaves its links showing the main name, since it's the same text.
  - So "Make main", which sends the old main name as a new row, drops the promoted name and sets `keepOldName`, swaps the two names, and every link shows what it did.
- **Alternate titles** ([3_alternate_names.md §4.2](../design/3_alternate_names.md#42-design-decisions)) are other titles a release, track or disc goes by: printed in another script or language ("シーナリィ"), or added in Slunk, like a translation, which isn't `printed`.
  - A release's are saved with its details, a track's with `setReleaseTracks`, `createTrack` and `updateTrack`, and a disc's with its disc title. Each list replaces the old one. Left out, they stay as they are, except one that's now the main title, which goes.
  - Titles are cleaned like other text, and a blank one is left out. They compare exactly, case included. A save is refused, with a message, when a title is given twice, or when one is the main title.
  - Each main title has a language: `titleLanguage` on releases and tracks, `language` on disc titles. A track's or disc's null means the release's. On an update, a `titleLanguage` left out stays as it is.
  - The release and track lists' search, and so the release picker, match the main title or any alternate title. `releasesTitled`, the import's check for duplicates, matches alternate titles too, ignoring case.
- **Languages** of names and titles (`nameLanguage`, `titleLanguage`, and each alternate name's or title's `language`) are BCP 47 tags, stored in canonical form by `languages.ts`: "JA-latn" becomes `ja-Latn`. A blank one is null, which means unknown. A malformed tag (`ja_JP`), one whose language isn't 2 or 3 letters ("japanese"), and `und` are refused. `languages` lists the tags in use, the most used first, for the language picker.
- **Release dates** are typed as `2006`, `2006-01` or `2006-01-10`, which also sets the precision (`dates.ts`). They're stored at midnight UTC on the first unknown day, and returned with only their known parts. An impossible date, like `2013-02-30`, is refused.
- **A release's artists, labels, formats and media** are saved as ordered lists, replacing the old ones: artists as credited (above), the others by id. The order is `position` for artists and labels, and insertion order for formats and media.
- **A release's tracks** are saved as a whole list (`setReleaseTracks`):
  - rows with an id update those tracks;
  - rows with a `fileId` or a `path` create tracks, registering paths first;
  - tracks left out are deleted, but their files stay registered.

  Before saving, the release's track numbers are shifted out of the way, so swapping two numbers can't trip the unique (release, disc, number) index.
- **Disc titles** are saved with the tracks, by `setReleaseTracks`, after them: a title needs a track on its disc ([reference/database.md](../reference/database.md#disc-titles)).
  - Given, they replace the release's titles, with their languages and alternate titles. Left out, they stay as they are.
  - A disc's alternate titles belong to its title: a disc with alternate titles and no title is refused, and they go when its title goes.
  - Titles are trimmed, and a blank one is left out, since a disc without a title has no row.
  - Two titles for one disc are refused.
  - A disc whose last track leaves it loses its title, whichever mutation moves or deletes the track. The database does that.
- **Covers, pictures and logos** can be set on their own (`setReleaseCover`, `setArtistPicture`, `setLabelPicture`), from a file id or a path. A path that isn't registered yet is registered in the same transaction, so a file the database refuses (one that isn't an image) isn't left registered. The other fields, and a release's file links, stay as they are.
- **Durations** are read from the audio file when a track is created, or when its file changes.
- **Track artists** are the track's own performers. Features are kept apart, and an artist can't be both on one track.
- **Who performs a track** follows design §4.3:
  - its own non-featured artists;
  - on a regular release with none, the release's artists, as credited there;
  - on a various-artists release, only its own, or nobody.
- **Credits** are lines ([2_credits.md §4](../design/2_credits.md#4-data-model)): a role as printed, and the artists who hold it, in order. "Engineer – Paul Barrett, Robbie Adams" is one line.
  - Saving a release's credits replaces them, and its tracks' credits too. A track's own are saved with the track.
  - Roles are trimmed. An artist given twice on a line is kept once, as first credited.
  - A save is refused, with a message, when a role is empty, when a line has no artists, or when two lines have the same role, ignoring case.
  - The repository inserts each line, then its artists numbered from 0, inside the save's transaction. The database checks at commit that every line has an artist at position 0 ([reference/database.md](../reference/database.md#credit-lines)).
  - `creditRoles` suggests the roles in use, for the editor: each spelling once, so "Mixed By" and "Mixed by" are both there, the most used first, at most 20.
  - An artist's credits are a row per line the artist is on, with the name it's credited with there, and `counts.credits` counts those lines.
- **Deletes** check what blocks them first, and the error says what does: "The artist is still used: release artist on 1 release, credited 2 times". Each entity's `blockers` field gives the same reasons ahead of time, for the delete dialog.
- **Import suggestions** (design §7.9) only read the folder:
  - `suggestRelease(folder)`: the most common album, date and album artist tags, or else the folder's name. Also the releases with that title already, and how many audio files, images and other files the folder holds. The title is kept whole, even with " = " in it: the frontend offers to split it. The check for releases with that title also tries each part, so "Scenery = シーナリィ" finds "Scenery".
  - `suggestTracks(folder)`: a row for each audio file, with disc, number and title from its tags. Without tags, they come from the path: `CD2/03 Title.flac` is disc 2, track 3, "Title". Each row also has its disc's title tag (`DISCSUBTITLE`, or `TSST` in MP3s), if the file has one.
  - **Artist tags** are matched by `suggestArtists()` ([3_alternate_names.md §7.7](../design/3_alternate_names.md#77-import-phase-3)), all of a folder's at once, in three steps: the main name exactly; then an alternate name exactly, credited with it; then either one ignoring ASCII case, credited as tagged, so "ALIKA", with only "Alika" known, is still printed as "ALIKA". The first step that finds anyone decides. Finding more than one artist picks none, and `matches` says how many there were.
  - A tag with " = " in it ("Ryo Fukui = 福居良") is matched by its first part. Its other parts that the artist doesn't have yet are `otherNames`, for the import to offer as alternate names. `equalsParts()` splits only at an "=" with spaces around it, since "E=MC²" is a title.
- **The release list** filters by format, medium, label, artist and tags, and they combine. Tag filters come from the tagging context, already checked. `releaseIds` returns every matching release's id, for selecting them all in a bulk edit.
- **The track list** filters by release and by tags.
- **A track's tags** are saved with the track, in the same transaction, when `createTrack` or `updateTrack` is given `tags`. Left out, they stay as they are.

## The tagging context

`src/slunk/tagging.ts` holds tag definitions and their values on releases and tracks (design §4.3 Tags). Each type, `text`, `number` or `date`, has its own definition table, so the same id exists once per type, and every function takes the type with the id. Each type also has a value table per owner, release or track (`release_text_tags`, `track_text_tags`, …). Releases and tracks share the definitions, so one Genre tag works on both. `tags_repository.ts` serves all of them.

- **Names** are unique across types, ignoring case. Each type's table enforces its own names, and the context checks the other two types when a tag is created or renamed.
- **Single or multiple.** Switching a tag to single-value fails while a release or track has several values. The context says how many do, and `multiValueOwners` lists them. The database refuses it too.
- **Deleting** a tag fails while any release or track has a value.
- **Values** are typed as text and stored by type:
  - text is cleaned (NFC, trimmed);
  - a number is like `8`, `-3.25` or `1e3`, and must be finite;
  - a date is `2006`, `2006-01` or `2006-01-10`, stored at midnight UTC on the first unknown day (`dates.ts`). There's no precision, so it comes back as a full day: `2006-01-01`.
- **A release's or track's values** are saved all at once (`setTags`, or `setTagsWith` inside another context's transaction), replacing the old ones:
  - blank values are left out, so a tag with none is removed;
  - a value given twice, ignoring case, is kept once;
  - a single-value tag with two values is refused ("Score takes one value");
  - values keep the order they were given in.

  They're read back grouped by tag, in tag name order.
- **List filters** (`tagFilters`), for releases and tracks, are checked and turned into ranges:
  - text: `equals` or `contains`, ignoring case;
  - numbers and dates: `equals`, or `min` and `max`, both included;
  - a date covers its whole year, month or day, so `equals: "2024"` is all of 2024, and `max: "2024-03"` runs through March 31.

  Each one is a `releases.id in (select release_id …)` (or `tracks.id`) over the value table, which uses its `(tag_id, value)` index. Several filters must all match, even on the same tag.
- **Text values** are counted for a tag's page (`tagValues`): each value with how many releases and tracks have it, the most used first. "Rock" and "rock" count as one, since values compare ignoring case.
- **Bulk edits** change one tag on many releases at once, in one transaction, and return how many releases changed:
  - `setTagOnReleases`: a single-value tag gets the value instead of its old one, and a multi-value tag gets it added. Releases that have it already, ignoring case, are left alone.
  - `removeTagFromReleases`: removes one value, or every value of the tag when none is given.
  - Ids of releases that don't exist are skipped.

## The library check

`src/slunk/library_check.ts` runs the library check (design §8, phase 4) over the media and catalog contexts. Running it writes nothing; each fix is its own mutation.

- **Missing and changed files.** Every registered file's size and mtime are read (`statFile`), 64 at a time. A file that isn't there is missing. One whose size or mtime isn't what was registered has changed.
- **Moved files.** When some files are missing, the check scans the library for where they went: the database's folder, and each top folder outside it that holds registered files (`../Other` for `../Other/A/x.flac`). Unregistered files the size of a missing one are hashed, and those with its hash are where it may have moved. Candidates with the same file name come first, and `likelyMove` is the only candidate, or the only one with the same name. When neither picks one, it's null and the user chooses.
- **Unregistered files** are files in a folder that holds registered files, which aren't registered themselves, by folder. Files that are where a missing file moved aren't listed again.
- **The catalog part:** releases with no artist (`withoutArtists`), and tracks on various-artists releases with no non-featured artist of their own (`withoutPerformers`), whom nobody performs (design §4.3).
- **Fixes:** `relinkFiles` points missing files at their new paths. `rehashFiles` reads changed files again, then the catalog reads the durations of the tracks whose audio they are (`readDurations`).

A scan only stats files and reads each folder's files together. It hashes only files the size of a missing one. On 20,000 small files in 2,000 folders, the check takes about half a second, and under a second when 110 files have moved.

## The database

### Connection

`openDb()` in `src/repo/db.ts` opens the app's connection. It sets `foreign_keys = ON`, `journal_mode = WAL` and `busy_timeout = 5000`, and fails if the database doesn't exist yet (`migrate` creates it). The server closes the connection on `SIGINT` and `SIGTERM`, which removes the `-wal` and `-shm` files.

Slunk writes only next to the database: the database file itself, its `-wal`/`-shm` files while it's open, and `slunk-backups/`.

The schema is described in [reference/database.md](../reference/database.md).

### Running migrations

The runner is `src/repo/migrator.ts`. `migrate` does the following:

1. Opens its own connection with foreign keys off, so a table rebuild can't cascade deletes.
2. Compares the migration files with the `migrations` table. It fails if an applied migration's file is missing, or if a pending file sorts before the last applied one.
3. If anything is pending, backs the database up with `VACUUM INTO` to `slunk-backups/slunk-<timestamp>.db`, next to the database. A database that didn't exist yet isn't backed up. Two backups in the same second get a `-2`, `-3`, … suffix. Then it removes the oldest backups beyond `SLUNK_KEEP_BACKUPS` (default 10). Only files named like its backups are removed; anything else in `slunk-backups/` stays.
4. Starts `BEGIN IMMEDIATE`, which takes the write lock, so the server and the CLI can't interleave. It reads what's pending again, then runs each `up` and records it in `migrations`, which it creates the first time.
5. Runs `PRAGMA foreign_key_check`, and rolls back if any row breaks a foreign key.
6. Commits.

So all pending migrations apply together or not at all. After a failure, the database is as it was, and the backup is still there.

`rollback` works the same way, running `down` for the last *n* migrations, newest first.

The server runs `migrate` every time it starts, so users never migrate by hand. `db:migrate`, `db:rollback` and `db:reset` then regenerate `src/repo/db_types.ts` with kysely-codegen. The server doesn't.

### Writing a migration

1. `npm run db:gen -- add_track_tags` creates `priv/repo/migrations/<timestamp>_add_track_tags.ts`, with empty `up` and `down` functions that take a `Kysely<unknown>`.
2. Write `up` with Kysely's schema builder:
   - End every table with ``.modifyEnd(sql`strict`)``.
   - Declare ids `.primaryKey().notNull()`, adding `.autoIncrement()` for entity tables. `NOT NULL` changes nothing in SQLite, but kysely-codegen needs it to type ids as `number`.
   - Name indexes `<table>_<columns>_index`, as the baseline does.
   - Use raw `sql` for triggers and for inserting rows. A migration has no DB types to build typed queries with.
3. Write `down` so it undoes `up`, or make it throw an explicit "irreversible" error.
4. `npm run db:migrate`, then `npm run db:rollback` and `npm run db:migrate` again, to check that both directions work.
5. Update [reference/database.md](../reference/database.md).

The rules:
- Never edit a migration once it has been committed. Write a new one.
- A migration runs inside the runner's transaction, so it must not start its own (`db.transaction()`).
- Migrations don't import app code. App code changes over time, and a migration must not. The exception is `src/repo/rebuild_table.ts`, which is part of the migration system.
- Starter rows, like the first release formats, are inserted by migrations, and nothing may depend on them. Sample data goes in `priv/repo/seeds.ts`.

### Changing an existing table

SQLite's `ALTER TABLE` only adds, renames and drops columns. Changing a column's type, CHECK, default or foreign key means rebuilding the table, with `rebuildTable()` from `src/repo/rebuild_table.ts`:

```ts
import { type Kysely, sql } from "kysely"
import { rebuildTable } from "../../../src/repo/rebuild_table.ts"

export async function up(db: Kysely<unknown>): Promise<void> {
  await rebuildTable(db, "artists", {
    // The complete new definition
    define: (table) =>
      table
        .addColumn("id", "integer", (col) =>
          col.primaryKey().autoIncrement().notNull()
        )
        .addColumn("name", "text", (col) => col.notNull())
        .addColumn("sort_name", "text", (col) => col.notNull())
        // …every other column and constraint
        .modifyEnd(sql`strict`),
    // New or changed columns, as expressions over the old table
    copy: { sort_name: sql`name` },
  })
}
```

It follows SQLite's recipe ([design §5.3](../design/1_introduction.md#53-changing-an-existing-table), with [Appendix B](../design/1_introduction.md#appendix-b-the-table-rebuild-needs-two-more-steps)):
1. It creates the new definition under a temporary name, `new_<table>`.
2. It copies the rows. Columns both definitions share are copied as they are, `copy` fills new or changed ones, and any other new column gets its default.
3. It drops the old table and renames the new one. It turns `legacy_alter_table` on for the rename, because other tables' triggers name the dropped table and would make the rename fail.
4. It recreates the table's indexes and triggers from their old SQL.
5. It puts back the `AUTOINCREMENT` counter, which the copy lowers to the highest id left. Otherwise ids of deleted rows would be reused.

Using it:
- **Generated columns,** like a credit line's `first_artist_position`, aren't copied: `pragma_table_info` doesn't list them, and the new definition creates them again.
- **Indexes and triggers** come back exactly as they were. To change one, or if it uses a column that's gone, drop it before `rebuildTable()` and create the new version after.
- **Other tables** keep working. Their foreign keys and triggers name the table, so they apply to the new one. If one of them uses a column you renamed or removed, recreate it too.
- **Foreign keys:** it only runs with foreign keys off, as the runner sets them, and throws otherwise. Rows that break a foreign key fail the runner's `foreign_key_check`, and the whole migration rolls back.
- **Don't change its behavior.** Committed migrations call it, and they must keep doing what they did. Add options instead.

### Generated DB types

`src/repo/db_types.ts` is generated from the database, and is committed. `.kysely-codegenrc.json` overrides two columns with string unions: `files.type` and `releases.release_date_precision`. Never edit the file by hand. Regenerate it by running a migration (or rolling one back).

### Seeds

`npm run db:seed` loads `priv/repo/seeds.ts`: five releases, with their artists, labels, formats and media, and the tags Genre and Score. Three of them are the examples of [3_alternate_names.md §4.1](../design/3_alternate_names.md#41-examples), so their artists have alternate names: "ALIKA" and the real name "Alika Milova", "福居良" in Japanese, misprints like "A. ## GraphQL

- **The schema** is the SDL in `src/slunk_web/schema/*.graphql`, one file per context, and every file there is loaded. `schema.graphql` defines `Query`, `media.graphql` defines `Mutation`, and other files add to them with `extend type`. The SDL's descriptions document the API.
- **Resolvers** live next to their SDL (`media.ts`, `catalog.ts`), are typed with `Resolvers` from `resolvers_types.ts`, and are listed in `schema/index.ts`. They turn GraphQL ids into numbers before calling a context.
- **Context:** resolvers get the app (`db`, `dbPath`, and each context: `media`, `catalog`, `tagging`) and `loaders`.
- **Loaders:** the DataLoaders in `loaders.ts` batch a page's related rows into one query per relation (design §7.3): a release list's artists, labels, formats, media and covers are five queries, whatever the page size. Every relation a field resolves goes through one. They're made fresh for every request, so nothing is cached between requests.
- **Codegen:**
  - `codegen.ts` maps GraphQL types whose resolvers return a context type, through `mappers`: `File` is a `FileRecord`, `Release` a catalog `Release`, and so on. They're imported with a `Model` suffix, so their names don't clash with the generated ones.
  - The `ID` scalar accepts numbers as output, so resolvers can return the database's ids.
  - Arguments and input fields with a default are typed as always present (`avoidOptionals.defaultValue`), since GraphQL fills them in.
  - After changing a `.graphql` file, run `npm run codegen` here, and in `slunk-fe/` too, since the frontend's types come from the same files.
- **Ids:** a field called `id` must identify its object. Apollo Client caches objects by type and `id`, so two objects with the same `id` would be merged into one. So:
  - `FileUse` names the id of the release, artist or track that uses a file `entityId`;
  - `Credit` has no id, since release and track credits come from two tables whose ids overlap;
  - `DiscTitle` has no id, since it's part of its release, and neither does `AlternateTitle`, which is part of its release, track or disc;
  - `LabelName`, a label's alternate name, has no id, since nothing refers to it. `ArtistName` has one, since a name is saved by its id;
  - `CreditedArtist`, an artist as credited on a release, a track or a credit line, has no id: it's part of its parent, and the same artist is credited differently on two releases;
  - release formats and release media are two types (`ReleaseFormat`, `ReleaseMedium`) behind one `ListItem` interface, so format 1 and medium 1 stay apart;
  - tags are likewise `TextTag`, `NumberTag` and `DateTag` behind a `Tag` interface;
  - `TagValues`, a tag with its values on a release or track, has no id;
  - `LibraryCheck` and its parts have no id, since they're worked out on each run.
- **Lists** take `page`, `perPage` (at most 200), `sort` (a column, `-` in front for descending), `q` and filters, and return `{ items, total }`. Pickers use the same queries with `perPage: 20`.
- **The API:**
  - `health`: the database's absolute path, and the latest applied migration.
  - `files`, `file`, `fileCounts`: registered files. `files(withoutTrack: true)` leaves out tracks' audio, for creating tracks.
  - `folder`, `folderFiles`: the library on disk.
  - `registerFiles`, `updateFile`, `deleteFile`: changes to the file records.
  - `artists`, `artist`, `labels`, `label`, `releases`, `release`, `tracks`, `track`, `listItems`, `listItem`: the catalog. `releases` filters by `format`, `medium`, `label`, `artist` and `tags`, `tracks` by `release` and `tags`. `releasesTitled` finds releases with a title, and `releaseIds` every release a filter matches. `creditRoles` suggests roles for credits. `Artist.alternateNames` and `Label.alternateNames` are their other names, `Release.alternateTitles`, `Track.alternateTitles` and `DiscTitle.alternateTitles` their other titles, and `languages` the language tags in use on names and titles. A release's and a track's artists, features and performers, and a credit line's artists, are `CreditedArtist`s: the artist, and `creditedAs`, the alternate name printed.
  - `createArtist`, `updateArtist`, `deleteArtist`, and the same for labels, releases, tracks and list items. `ArtistInput` and `LabelInput` take the name's language and the alternate names, and `ArtistInput` `keepOldName`. Release, track and credit inputs take artists as `CreditedArtistInput`s: an `artistId`, and `creditedAs`, the name as printed.
  - `setReleaseTracks`, `setReleaseFiles`, `setReleaseCredits`: a release's edit tabs. Files can be given by path, and they're registered first. `setReleaseTracks` also takes the disc titles, which `Release.discTitles` reads.
  - `setReleaseCover`, `setArtistPicture`, `setLabelPicture`: only the image, from a file id or a path to register first. The pages set an empty one with them.
  - `addArtistName`: adds one alternate name after the others, as the import does with a tag's other names. It's refused when the artist has the name already.
  - `catalogTotals`: the dashboard's numbers.
  - `releaseSuggestion`, `trackSuggestions`: the import's prefill. Their artists are `ArtistSuggestion`s: the name matched, the artist if exactly one matched, the name to credit it with, how many matched, and the other names to offer.
  - `tags`, `tag`: tag definitions, of one type or all three. A `TextTag` has its `values`, counted. `tagsByRef` gets tags by type and id, for naming a list's filters.
  - `createTag`, `updateTag`, `deleteTag`, and `setReleaseTags`, the release's Tags tab. `Release.tags` and `Track.tags` read them, and `TrackInput.tags` sets a track's.
  - `setTagOnReleases`, `removeTagFromReleases`: bulk edits.
  - `libraryCheck`, and its fixes `relinkFiles` and `rehashFiles`.
- Opening `http://127.0.0.1:4000/graphql` in a browser shows Apollo Sandbox, for trying queries.

## Conventions

### TypeScript

Node runs the code by stripping its types, which shapes the TypeScript settings:
- **`erasableSyntaxOnly`:** no `enum`, `namespace` or parameter properties.
- **`verbatimModuleSyntax`:** use `import type` for types.
- **Imports:** relative, ending in `.ts` (`./db.ts`). There's no path alias, since Node wouldn't resolve it.
- **`strict`**, and `tsc` only typechecks (`noEmit`).

File names are `snake_case`, as in Phoenix.

### Formatting and linting

- **Prettier:** the same settings as `slunk-fe`, without the Tailwind plugin. Run `npm run format`.
- **ESLint:** the recommended JavaScript and typescript-eslint rules, with Node globals. Run `npm run lint`.

Both skip the generated files.

### Install scripts

`package.json` lists packages under npm's `allowScripts`:
- `better-sqlite3` is allowed, because its install script fetches the native binary.
- `@apollo/protobufjs` is denied, because its script only prints warnings.
